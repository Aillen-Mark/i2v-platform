## 第一批具体顺序

1. **003**。提供 `config.py`、`sessions.py`、`moderation.py`、交接日志和对应测试的逐文件实施计划。此单预期无数据库迁移、无前端页面变更，保留开发 Mock。生产 Cookie 与 004 的 HTTPS 契约对齐。
2. **005**。盘点已运行实例的 Binlog、备份、连接和磁盘状态前，先用隔离环境建立提交和还原基准。计划应说明耐久参数、备份目录、异地目标、密钥保留、迁移基线及回滚。上线参数评估单独进行。
3. **001**。和 002、007 先审查公共状态和数据契约，再单独实现扣额、Work、Outbox 的原子提交与至少一次派发。明确旧 `queued` 的识别方式、发布后未被消费的重新派发、消费去重，以及逐笔扣退记录。旧数据先只读盘点，回填单列审批。

## 每单工作流

重读模块与上下游 → 提交文件、新增项、数据、HTTP、前端、Docker、旧数据和回滚影响 → 等确认 → 小步实施 → 目标测试与相关集成测试 → 检查 Git diff/status → 更新 Issue 和验收报告。迁移采用版本化、向后兼容路径，生产更新前留备份和恢复证据。

## 生产资源起点

4 核、16 GB 起步生成并发 1、转码并发 1；结合 API P95、生成积压、FFmpeg RSS/CPU 和临时磁盘调参。100 GB SSD 的备份、Binlog、对象、临时文件和容器日志分配需有上限和告警。按十进制单位计算，5 Mbps 下 100 人各下载 6.65 MB 理论至少约 18 分钟，各下载 30 MB 约 80 分钟，未计 API 争抢及协议开销。目标存储和签名域名优先提前做专门验证。

- 第一批是否按 003、005、001 顺序开始。每个 Issue 的实施仍由对应计划单独批准。

- 无音轨成片采用静音 AAC 还是允许无音轨。生产视频签名直出的对象存储或 CDN 选型。
- MiniMax 未知请求的对账负责人、等待时限与退款规则。真实 API 验证使用独立账号和明确额度。
- 历史考生归档、旧 `queued` 和孤儿对象的处置原则。审批前仅盘点。
