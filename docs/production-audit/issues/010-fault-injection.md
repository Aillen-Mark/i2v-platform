## 问题背景

正常路径和 HTTP 基础压测已存在。目标新增端到端故障恢复与真实资源边界的可复现证据。

## 实际代码依据

默认 pytest 仅发现 `backend/tests`；Worker 测试需显式指定。现有百人脚本等 Mock 出片，下载只测 Range 首块与 TTFB。未发现生产 Compose 的重启演练或真实 MiniMax 容量测试。[pytest 配置](../../../backend/pytest.ini#L8) · [Worker 单测](../../../backend/worker/test_worker.py) · [压测](../../../scripts/load_test_100.py#L154)

## 风险说明

首块延迟、Mock 结果和进程重启并不能证明完整下载、上游不重复生成、账本一致性或恢复时间目标已经达到。

## 改造目标

覆盖关键持久化边界与有限资源下的系统验收。所有结果按实际执行环境和验证类型记录。

## 涉及文件

`backend/tests/`、`backend/worker/test_worker.py`（保留现有用例）、`scripts/` 中隔离验收脚本及 `docs/production-audit/acceptance-criteria.md`。

## 修改范围

先搭建隔离 MySQL、Redis、Celery、MinIO、FFmpeg 的故障注入环境，补齐崩溃、重投、超时、对象不一致和回滚测试。分别记录 HTTP、提交、真实生成、完整下载四种负载。另行审批预算后运行真实 MiniMax 抽样。

## 明确不修改的内容

测试不连接线上数据库、生产队列或真实考生对象，不覆盖线上配置。不删改现有测试以改善结果。

## 数据库影响

专用测试数据库和存储前缀/桶，清理仅针对测试创建的数据。用快照、账本及恢复实例对比证据。

## 兼容性要求

保留已有 38 项业务回归和 6 项 Worker 用例。真实依赖、模拟上游、真实上游及静态证据分别报告。

## 测试要求

注入 API/Dispatcher/Worker 退出、Redis 重启或数据丢失、MiniMax 接单丢响应、DB 提交失败、无音轨/坏片、MinIO 上传失败和备份恢复。在目标规格上验收宿主重启、吞吐和稳定性。

## 验收标准

- [ ] 每个验收场景有命令、版本、运行环境、证据和明确状态。
- [ ] 账本与已知上游提交次数对账，重复扣额、退款及虚假成功均为 0。
- [ ] Ubuntu 资源数据与恢复实测符合批准目标，缺项记录原因。

## 回滚方案

验收脚本在隔离环境执行。出现异常停止负载，恢复测试快照，保留日志和报告；回退应用用 004/005 的已签核方案。
