# 007 数据库租约与任务恢复扫描

**优先级** P0
**审查结论** 部分已有，剩余问题已确认。晚确认、时间限制和扫描器存在；缺少数据库接管与完整阶段。
**发布状态** 待批准

## 问题背景

消息晚确认用于重新投递，无法独立证明谁拥有 Work，也无法恢复所有已持久化的阶段。

## 实际代码依据

Celery 配置晚确认、进程退出重投和 Beat。Work 锁和开始时间存 Redis；扫描器查两小时以上的 queued 和约 690 秒无更新的 running，再向同一生成队列投递。Worker 读取 Work 时内连接考生。[任务配置](../../../backend/worker/tasks.py#L25) · [扫描与锁](../../../backend/worker/state.py#L113) · [考生连接](../../../backend/worker/state.py#L80)

## 风险说明

Redis 锁丢失或过期后，新旧执行者可能争抢。恢复扫描会受大任务积压影响。物理删除考生会使历史 Work 和扣退关联不可用。

## 改造目标

用 MySQL 租约、领取世代及合法转换约束接管；将恢复扫描与生成隔离。消除依赖现存考生行才能结算的缺口，设计审查决定归档或保留快照。

## 涉及文件

`backend/worker/state.py`、`tasks.py`、`pipeline.py`、`backend/app/models/work.py`、回调、迁移和集成测试。考生档案接口的任何变更需在实施计划单独标明。

## 修改范围

持久化开始、心跳、接管和阶段时间。用条件更新拒绝过期所有者写入，保留状态轨迹；给过期、孤儿及挂起任务独立告警。旧 `queued/running` 先只读分类；将正在处理的考生归档策略和对象键快照纳入评审。

## 明确不修改的内容

不批量改历史、不凭 Redis 锁认定终态、不重构登录或整个配额后台。调额竞态在单独子任务评审，避免夹带修改。

## 数据库影响

扩展租约和阶段字段并按扫描路径建索引。定义存量兼容读取、隔离旧消费者和回填审批。存在历史孤儿时，仅报告并隔离，默认不静默补造关联。

## 兼容性要求

对旧 API 输出保持已知状态兼容；内部 `uploading/retry_wait/submission_unknown` 的页面映射需要契约审查。终态不可被迟到写入覆盖。

## 测试要求

真实 MySQL + Redis + Celery 执行双 Worker 竞争、SIGKILL、Redis 重启、租约断续、旧执行者迟到、删除考生后任务可结算，以及已上传任务接管。

## 验收标准

- [ ] 在批准恢复时间内扫描并接管，旧租约无法落库终态。
- [ ] Redis 丢失后从 MySQL 重建调度，重复交付不重复生成、退额或覆盖成功。
- [ ] 旧记录的处置可查询、可审计。

## 回滚方案

停新派发，记录活跃租约、未知请求、待上传对象和需接管任务。保留新增字段，排空或人工处置不能由旧 Worker 识别的阶段，再恢复旧消费者。
