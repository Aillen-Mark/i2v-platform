# 005 MySQL 提交持久性与备份恢复

**优先级** P0
**审查结论** 已确认，静态审查；未执行断电、异地备份或恢复。
**发布状态** 待批准

## 问题背景

MySQL 是配额和作品权威记录。当前参数为本机压力测试优化，生产要优先保护已应答事务。

## 实际代码依据

Compose 默认 `innodb_flush_log_at_trx_commit=2`，允许 500 连接，初始化只在空卷导入 SQL。API 单进程异步池配置为 20+30，Worker 同步池为 5+10。仓库未发现迁移和备份还原脚本。[MySQL 配置](../../../docker-compose.yml#L10) · [连接池](../../../backend/app/core/database.py#L23) · [建表](../../../docs/schema.sql)

## 风险说明

主机或掉电故障会损伤尚未刷盘的已确认事务。仅有本机卷无法覆盖磁盘失效。盲目改 Binlog、清理策略或密钥会缩小恢复窗口。

## 改造目标

确定生产刷盘和 Binlog 策略，建立自动备份、异地保留和可测量的恢复。提供后续增量迁移的版本约定。

## 涉及文件

生产 MySQL 配置、`backend/app/core/database.py`（如需做池参数化）、迁移基线与版本约定、`deploy/ubuntu/backup.sh`、`restore.sh`、运维说明。

## 修改范围

先盘点实库版本、备份、Binlog 状态、磁盘及连接，再在隔离环境评估 `innodb_flush_log_at_trx_commit=1` 和启用 Binlog 时的 `sync_binlog=1`，确定预算、告警与保留。恢复验证关键表行数、校验值和抽查对象映射。

## 明确不修改的内容

不在本单迁移 Work 状态、Outbox 或尝试表，不恢复覆盖生产卷，不删除历史数据，也不调整现有生产实例。

## 数据库影响

策略会改变写入延迟与磁盘消耗，迁移基线应兼容已初始化数据库。先备份并在新实例验证再应用配置。Binlog 和库备份不得仅保存在宿主。

## 兼容性要求

保留 MySQL 8.0、UTC、字符集、现有 SQLAlchemy 驱动和 API；生产池与开发池可以分别配置。

## 测试要求

隔离真实 MySQL 上检查运行参数与版本、备份校验、全量和时间点恢复、配额与作品对账、耐久模式下 100 并发提交延迟。

## 回滚方案

保留原配置快照、旧版本镜像和值班核对表。应用变更前验证回退路径。不因性能回滚到低耐久生产模式，相关批准另行记录；备份恢复用新实例并比对后再切服务。

## 实施计划

005 先交付可复跑的 MySQL 基础备份和独立库恢复。将 Compose 中 MySQL 刷盘改为持久性优先，SYNC_BINLOG 配置明确。新增 `deploy/ubuntu/backup.sh`、`restore.sh` 和运维说明。备份采用 InnoDB 一致性快照、压缩、校验清单，并可复制到已提供的异地挂载。恢复只导入新数据库，确认地址和数据库名后再运行。

本单无 Schema 或历史数据修改，无 API 和前端影响。保留原有 Windows 入口和数据卷。上线前需保存当前 Compose 参数、库备份和 Binlog 策略。若需回滚应用配置，恢复上一版 Compose，已有备份、日志和数据库卷保留。生产调度由 004 接入，RPO/RTO、Binlog 连续归档与远端保留依赖实际基础设施和演练。
