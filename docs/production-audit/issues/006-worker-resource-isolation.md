# 006 生成和转码资源隔离

**优先级** P1，生产资源门禁
**审查结论** 已确认，静态审查。已有 FFmpeg 线程和单文件大小限制，容量结论待压测。
**发布状态** 待批准

## 问题背景

生成 Worker 从上游提交、轮询一路执行到转码和存储，等待上游与本机 CPU 竞争绑定在一个进程槽。

## 实际代码依据

Worker 默认一条生成队列，`generate()` 直接进入 `upload_and_finish()`。README 生产样例并发 25。FFmpeg 已限制滤镜和编码线程，缺少跨任务转码上限与容器预算。[任务](../../../backend/worker/tasks.py#L25) · [流水线](../../../backend/worker/pipeline.py#L140) · [媒体](../../../backend/worker/media.py#L34) · [启动示例](../../../backend/worker/README.md#L24)

## 风险说明

多个生成同时完成时会产生 CPU、内存、磁盘和 I/O 峰值，挤压 API。仅将本地并发设为 1 又会让上游轮询长期占用唯一槽并延长排队。

## 改造目标

独立的上游并发与本地转码预算。起步生成并发 1、转码并发 1，使用上机测量调整。

## 涉及文件

`backend/worker/tasks.py`、`pipeline.py`、`media.py`、`config.py`、生产 Compose 资源配置及资源验证脚本。

## 修改范围

拆分 Celery 队列和处理权限，使用已持久状态安全转交。转码采用有界临时目录、进程数和线程，收集 RSS、CPU、磁盘和端到端等待指标。单机部署前按预算设置 API 和数据库连接池。

## 明确不修改的内容

不按 MiniMax 上限直接设置本地并发，不引入新队列系统，不改考试配额或视频画幅行为。

## 数据库影响

复用 007 的阶段和租约。如需额外字段，先审查迁移；不改已有成功作品。

## 兼容性要求

旧 Celery 消息要在切换期间可消费，或经盘点后再停止旧消费者。MinIO 对象路径和 API 保持兼容。

## 测试要求

在 4 核 16GB 隔离主机同时做大文件转码、100 人 HTTP 登录与提交、下载；测峰值 RSS、CPU、临时空间和 API P95。验证并发上限和背压。

## 验收标准

- [ ] 生成与转码队列各有独立且可测的并发上限。
- [ ] 达到上限时可排队，负载不导致 OOM 或 API 饥饿。
- [ ] 公布实测容量、余量和调大并发的阈值。

## 回滚方案

停止新阶段交接，盘点活动 Work 和待转码任务，排空或按租约重新接管。切回单 Worker 低并发，保留持久中间状态。
